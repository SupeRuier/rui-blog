::: tldr
具身系统里最容易被含糊处理的一步是「部署之后」。数据飞轮常被简化成「把现场数据收回来训练」，但真正决定这条循环能否成立的不是采集量，而是更靠后的三件事：**证据能不能回放、失败能不能归因、改进能不能过门禁**。缺任意一环，链路还在转，只是它已经不再闭合。

三个核心判断：

- **闭环的最小单元不是「一次成功」，而是一次任务尝试及其恢复链。** 重试与恢复必须保留父子关系——把多次尝试合并成一次成功，等于把恢复成本从记录里删掉。
- **失败可用，但不默认可训。** 只有能构造可靠监督或偏好信号的失败才适合进训练；其余分别流向评测反例、诊断线索和采集指令，三种用途要求三种不同的前处理。
- **改进有多个出口，不是只有模型。** Tool / Harness / Memory / Model / Policy / Evaluator / Hardware 六类出口对应不同的错误结构；把全部失败都路由到模型，是这套系统里最贵的默认选项。

本文给出一条完整链路：统一 Experience 单元 → Raw / Semantic / Derived 三层 → 独立验证与归因 → 多出口候选变更 → 回归门禁与灰度 → 新的 Experience。
:::

::: question
一次真实部署产生的记录，要经过哪些对象和接口，才能变成一个通过门禁的新版本？
:::

「数据飞轮」这个词在具身领域被用得很宽：回收一次现场数据、把一批失败样本入库、跑一次微调上线，都可以被称为飞轮在转。但把链路摊开会发现，采集只是入口。后面还有三段更难的：现场证据能不能被回放，失败能不能被定位到具体层级，候选改进能不能在固定条件下被证明优于上一版。少掉任何一段，系统仍然在产生数据，只是判断没有跟着增长——那是数据流水线，不是闭环。把数据规模当作主要瓶颈的公开判断并没有错[@3]，但它描述的是入口；入口之后的判断链，才是本文的对象。

本文只讨论「回传之后」。数据从哪里来、各类来源支撑什么能力，见[具身智能的数据体系](embodied-data-pyramid.html)；一次任务怎么判分、怎么逐层归因，见[具身系统评测：从模型能力到部署现场](robot-agent-evaluation.html)；经验如何构成自我改进、以及「数据回传不等于自我改进」这条判据，见 [Agent RSI 与 Robo RSI](agent-robo-rsi.html)。这三篇分别回答来源、测量与分类，本文回答**处理链路**。

先给出全文的总架构。它是一条从现场执行回到现场执行的闭环：中间经过**证据、解释、改进**三段处理，最后必须过门禁，才能成为下一版系统的一部分。后面各章按这张图自上而下展开。

## 01 · 先划边界：什么不算数据闭环

我把数据闭环定义为一个**闭合的实验过程**：系统在任务与环境条件下执行，产生可回放的证据；评价器给出与目标对应的结果；归因机制提出可检验的改进假设；候选更新在固定条件和保护集上比较；通过门禁后进入下一轮部署。把部署现场本身当作持续评测的来源、按站点与版本切片观察，是这类系统公开实践中的共同做法[@1]。

这个定义里，「数据回流训练集」只覆盖了第一环。它缺少结果验证、归因和回归中的任意一环，就会退化成流水线。一个很实际的检验方式是问：**这一轮收集的数据，具体改变了哪一个决策，这个改变又是被哪一批固定任务证明的？** 答不上来，说明采集端在动、改进端没有对应的证据。

为了让后面的设计有共同坐标，先固定四组维度：

::: list method-list
1. **任务层级：**workflow → subtask → skill → action。指标和数据切片都按这四级组织，否则「成功率」不知道在说哪一层。
2. **系统层级：**model → harness → tool → controller → hardware。这是改进出口的选择空间，也是归因的责任层级。
3. **证据层级：**raw → semantic → evaluation。证据与解释必须分开存放，后者可以被重算，前者不可以被覆盖。
4. **时间与分布：**单次执行 → 长时运行 → 跨站点与跨机器人。同一模型在两个站点就是两个部署单元，性能差异必须能区分出是模型、现场还是设备造成的。
:::

## 02 · 统一 Experience：把物理行为和 Agent 决策装进同一个单元

只记录物理动作的 Episode 不足以支撑上面的四组维度。它至少缺三样东西：**决策上下文**（当时 Agent 看到什么、为什么这么选）、**独立验证**（谁判定成功、依据是什么）、**系统状态**（模型、Harness、工具、控制器、固件、标定的版本，以及硬件健康）。缺了这些，一条轨迹只能说明「机器人做了什么」，不能说明「系统为什么没做对」。

因此基础数据单元应从 Episode 扩展为 **Experience**：一次任务尝试及其恢复链的顶层对象。一次长任务可以包含多个 Episode，一个 Episode 可以包含多个 Agent Step、Skill Segment 和物理 Action Chunk。把 Agent Trace 与物理 Episode 同步记录、并在验证之后把轨迹沉淀为程序、记忆或 Harness 修订，是 physical coding 一类公开工作的主张[@4][@5]；这里把它固定进数据模型。Experience 至少要覆盖六个域：

| 域 | 关键字段 | 设计约束 |
| --- | --- | --- |
| 身份与上下文 | experience_id、task_run_id、site_id、robot_id、操作员、SOP、目标与约束 | 全局唯一；快照任务规范与环境配置 |
| 版本与配置 | model、policy、harness、tool、memory、controller、firmware、calibration、evaluator | 记录不可变版本及变更时间 |
| Agent Trace | 观察引用、world state、plan、tool call / result、verification、recovery、final decision | 每步含时间戳、证据引用与可见性边界 |
| Physical Episode | 多相机、深度、音频、关节状态、力 / 电流、命令、控制器状态、系统日志 | 原始流分块存储；时钟偏移可估计 |
| Semantic Structure | workflow / SOP step 边界、对象状态、事件、失败模式、人工介入 | 标签可多版本、可追溯 |
| Evaluation | 成功、质量、安全、时延、能耗、干预、verifier 证据、硬件健康 | 区分观察值、推断值与客户验收结果 |

**重试不能被合并。** 一个 `task_run_id` 标识一次任务请求，一次请求可以包含多个 attempt，每个 attempt 由若干 Episode 和 Agent Trace 片段组成；重试与恢复通过 `parent_attempt_id`、`recovery_of_step_id` 关联，且不覆盖原始失败片段。这样系统才能同时报出业务口径的最终完成率，和能力口径的首试成功率、恢复成本与人工介入率——把它们合并成一个成功率，等于宣称「有人扶着也能干」和「能自己干」是同一件事。

**完整性分级是接口约定，不是数据质量评分。** 并非每条 Experience 都有全部模态，因此需要显式声明级别：`L0` 只有任务与结果摘要，`L1` 增加关键事件与版本，`L2` 增加时间对齐的 Agent Trace 与物理流，`L3` 增加可回放的原始证据与独立验证。每类下游声明自己的最低级别——把「缺失模态」当成「该模态不存在」，是后续所有错误归因的起点。

**三种「结果」必须分开存。** `agent_claim` 是 Agent 自述完成，`verifier_result` 是独立验证器的判断，`acceptance_result` 是客户或任务规范的最终验收。三者在长程任务中经常不一致，而这种不一致本身就是证据：它既是修订 evaluator 的输入，也是区分「策略失败」与「验证器错误」的唯一依据。

## 03 · 三层分层：Raw、Semantic、Derived

证据与解释混用，是数据系统最常见的一种腐败：一旦语义标签可以覆盖原始记录，出现争议时就没有可回退的真相。因此数据分三层，各自的更新规则不同。

**Raw Execution Record——追加写、不可变。** 边缘端在正式 Episode 之外维持环形缓冲，异常、人工接管或安全事件触发前后窗口固化。每条记录带采集时钟、设备时钟、序号、采样率、丢包与缺帧标志、内容校验；先落本地，再异步上传并校验后清理。两个容易被省略的字段其实最关键：**上传失败、断点续传、采样降级与保留窗口必须一并记录**，否则只有「顺利上传的执行」进入分析，形成系统性的选择偏差。高带宽影像的通用做法是：保留事件触发的高保真窗口，同时维护覆盖全班次的低成本索引流，且触发逻辑与丢弃策略可审计。

**Semantic Experience——版本化、可重算。** 对齐视角后做任务层级分段、对象与状态抽取、工具执行状态映射、独立结果验证与失败分类。这里有一个必须坚持的区分：**event 与 state 不是一类东西**。event 是「抓取尝试、放置、重试、接管」等有边界的发生；state 是「物体位置、夹爪占用、任务进度」等在区间内成立的判断。标签至少携带 `label_version`、`evidence_refs`、`confidence`、`source`、`review_status` 五个字段，自动标注先给出置信度与证据帧，低置信度、验收冲突、安全事件与重大回归进入人工审阅。标注质量要靠分层抽检估计，并分站点、分步骤、分失败类型报告误差——只给一个总体准确率，无法支撑任何归因。

**Derived Data Products——按用途生成。** 下游不是共用一份「高质量数据集」，而是各自要求不同的前处理：

| 产品 | 面向用途 | 最小质量门槛 |
| --- | --- | --- |
| 评测样本与切片 | 持续评测、回归、发布门禁 | 验收标准与版本齐全，结果有证据 |
| 技能训练片段 | policy / VLA 微调、控制器优化 | 动作与观察同步，干预与故障标签明确 |
| 决策轨迹 | planner / tool / harness 优化 | 输入可见性、工具结果、验证与恢复链完整 |
| 记忆与程序候选 | SOP、环境知识、可复用流程 | 多次独立验证，适用边界明确 |
| 健康与运维序列 | 漂移预测、预防维护 | 硬件配置、校准与维修记录可关联 |
| 采集任务队列 | 主动学习、课程生成 | 覆盖缺口、预期价值、成本与风险可估计 |

**下游不能共用一个「高质量」定义。** 评测集的核心是口径稳定、样本可追溯、与训练隔离；训练集的核心是监督信号正确、分布覆盖充分、且不含不应学习的故障；运维数据则必须保留时间连续性与部件谱系。如果在进入下游之前统一执行「只保留成功样本」，失败归因与恢复学习就被一起删掉了；反过来统一执行「所有失败都进训练」，又会把硬件故障和验证器错误写进模型目标。因此每个派生产品都要记录来源 Experience、转换版本、筛选谓词、排除原因与数据用途。

三类前置项值得单独点出：**评测数据**要先冻结任务定义与验收谓词（什么算完成、质量阈值、允许重试几次、人工介入如何计分），再做切片设计与泄漏检查；**训练数据**要保证观测与动作在执行时刻严格对齐，区分策略命令、控制器修正与真实运动，并重建每一步决策时**实际可见**的信息；**程序、记忆与工具修订**则分别需要前置条件与失效边界、来源与有效期、以及能在相同状态下重放失败的接口契约。

## 04 · Failed rollout：从故障分类到可检验的归因

失败记录至少分成六类：任务失败、局部步骤失败但已恢复、证据不足、超时或预算耗尽、安全停止、记录损坏。这个分类的意义在于**阻止过度归因**：超时只说明停止条件被触发，不自动等于能力失败；记录损坏既不是模型问题也不是现场问题。恢复前后的片段必须成对保存，并记录恢复动作是否真正改变了目标状态。

归因不是给失败贴一个标签，而是回答「如果改变某一因素，结果是否会改变」。语义标签回答「发生了什么」，归因回答「为什么」。所以结构应当是：**现象 → 候选原因 → 证据 → 反证 → 责任层级 → 建议干预**。执行顺序上，先排除时钟、传感器与评测器错误，再依次检查环境变化、硬件漂移、执行控制、工具接口、世界状态估计、规划与策略；允许多因并存，**禁止仅凭最终失败标签直接判定模型责任**。

| 失败类型 | 关键证据 | 优先去向 |
| --- | --- | --- |
| 抓取滑脱 | 接触前后视觉、力 / 电流、末端轨迹 | 控制与夹爪；技能训练 |
| 错误对象或步骤 | Agent 可见观察、world state、SOP、tool call | 感知与状态表示；planner / harness |
| 验证误判 | 原始结果、verifier 输入输出、人工复核 | 评测器修订与保护集 |
| 现场分布漂移 | 站点、光照、物料、设备版本与历史基线 | 主动采集、域适配 |
| 硬件退化 | 校准偏差、温度、电流、振动、维护史 | 维修与硬件参数更新 |

因果结论无法靠聚类或看一段视频得到。较稳妥的做法是先建立候选因果图，再用对照证据缩小假设：同一模型跨机器人比较、同一机器人跨模型比较、维修前后比较、相同物料在不同站点比较，必要时在仿真或受控现场重放。每条结论都应保留支持证据、反证、未控制的混杂因素与置信等级。

**一次失败有四种用途，前处理互不通用。** 第一，作为评测反例，防止后续版本重复同类错误；第二，作为诊断样本，定位硬件、工具或验证器故障；第三，作为训练样本，但仅在能构造可靠监督或偏好信号时使用；第四，作为数据采集指令，指出需要补充的场景、示教或传感器。只有失败事实而没有可靠改正信号时，它更适合作为评测反例或采集线索，而不是训练目标。恢复轨迹尤其值得单独保存——长时运行表现更多由恢复能力决定，而不是由一次性成功率决定。公开的自主改进工作也正是把「自主采集 + 筛选」当作技能持续改进的入口[@9]。

## 05 · 评测与 observability 的分工

两者共享原始证据，但要回答不同的问题，因此维护不同的版本与质量门槛。

**Evaluation 回答「是否更好」**，所以必须有冻结口径、对照版本和预先定义的验收指标。发布评测固定任务、环境、随机种子、预算与评测器版本，候选与父版本在同条件下比较；正式发布决策既看平均成功率，也看最差切片、安全指标与置信区间。**observability 回答「哪里变了」**，所以需要高覆盖、可下钻的事件与遥测，并允许快速迭代以发现问题——它不应被当作发布判据。

指标必须保留层级与分母：任务级成功率的分母是 task run，步骤级失败率的分母是相应 SOP step 的尝试次数，恢复成功率的分母是进入恢复的失败次数，三者不可混用。长时工作还应报告单位时间合格产出、**无人工干预时长**、连续工作失败间隔与单位合格产出的能耗[@2]；稀有安全事件同时报告绝对事件数与暴露量，而不只展示百分比。

**硬件健康既是一等维度，也是混杂变量。** 一个恰好跑在老化夹爪批次上的 checkpoint，其成功率下降不应被直接解释为策略退化。健康状态应同时作为评测切片与训练筛选条件：既报告包含全部生产设备的真实业务指标，也报告控制硬件状态后的模型比较结果。维修事件、零件更换与重新标定要进入版本谱系，使「维修后改善」与「模型更新后改善」可以分开分析。

## 06 · 采集课程：refinement 与 acquisition 的空白含义不同

采集调度基于一张能力矩阵，但矩阵上的「空白」对应两件不同的事，系统必须显式区分这两类采集请求。

**Capability refinement** 针对已会但不稳定的技能：空白是「缺少可靠性证据」，因此优先采集失败边界、站点漂移与恢复样本，把长尾可靠性补上。**Capability acquisition** 针对新任务或新物体：空白是「尚无可执行能力」，因此先定义成功判据与安全边界，再用示教、仿真与受控现场试验建立初始覆盖。

两类请求共用一个调度器，但估计的对象相同：信息增益、成本、风险与可迁移性。这里的成本要按[数据体系](embodied-data-pyramid.html)那篇的四轴来算——采集成本、重置成本、标注成本与**反馈速度**，其中反馈速度决定迭代能做多少次。缺口识别的分辨率决定了这些预算投向哪里；分辨率不够时，采集投入会均匀摊到所有方向上，看起来也没有浪费，只是效率低到看不见。

自主采集用于自我改进已有公开实例[@7]；而大规模真机采集的公开实践表明，安全约束必须作为采集系统的一部分来设计[@8]，而不是采集之后再加的补丁。

## 07 · 多出口自改进与准入门槛

改进不等于更新模型。按错误结构路由到不同出口，是这套设计里最省钱的一条原则。

| 改进出口 | 触发信号 | 候选变更与验收 |
| --- | --- | --- |
| Tool | 接口失败、动作粒度不适、能力缺口 | 新增或修订工具；沙盒契约测试与现场回归 |
| Harness | 观察路由、状态维护、验证或恢复逻辑失效 | 程序 / 工作流修订；静态检查、保护集、回滚 |
| Memory | 重复出现的场景知识或稳定成功经验 | 条件化记忆；检索准确性与过期机制 |
| Model / Policy | 广泛或系统性的决策 / 动作误差 | 筛选训练集并训练；离线、仿真与现场分层评测 |
| Evaluator | 评分与真实验收冲突 | 独立标注、盲审、冻结对照集 |
| Embodiment / Hardware | 重复机械故障或传感不足 | 维护、校准或硬件设计；跨设备验证 |

这个表其实是 [RSI 六轴](agent-robo-rsi.html#taxonomy-limits)里 WHAT 轴的工程投影[@6]：**局部、可复现的工具参数或控制流程错误，优先考虑 Tool / Harness 修订**；跨任务反复出现的环境事实与操作规则，适合进入带适用条件的 Memory；只有广泛分布的感知或动作误差，才更可能需要模型或策略更新；而评价与真实验收不一致时，首选动作是修订 Evaluator。路由不是单标签分类，复杂失败可能需要联合更新；关键是为每个候选变更写出**可证伪的预期**：它应改善哪些切片、可能伤害哪些保护切片、怎样判断它无效。

候选变更的准入分五级：静态检查 → 可复现案例 → 冻结回归集 → 未参与开发的保护集 → 受控现场灰度。每轮遵循生成候选、静态校验、复现与回归、冻结基线对比、有限灰度、正式发布；被拒绝的候选同样保留反例与诊断，被接受的候选写回版本谱系并生成下一轮采样与评测任务。有两类变更需要额外检查可比性：**候选修改了评测器**，必须在独立人工或冻结判定集上校验评分口径，否则可能只是换了尺子；**候选修改了 Harness**，必须确认观察路由与工具调用预算的变化是否影响与前版的可比性。

## 08 · 端到端链路与落地阶段

开头那张总架构图面向浏览，用站内的 HTML/CSS 图形语言画，读起来快也随页面自适应；下面这张是它的**原始 mermaid 表达**，保留逐条连线与标注，适合对照核对。两张图是同一套设计的两种表达，不引入新信息。

Raw 层不因标签或模型更新而改变；Semantic 与 Derived 层可以按版本重算；发布门禁只接收带有明确来源与独立验证结果的候选变更。

::: diagram flywheel-loop
图 · 数据闭环的端到端链路：现场执行 → 证据链 → 解释链 → 改进链 → 门禁与灰度 → 新版本部署。纵向可滚动，也可放大查看逐条标注。
:::

链路的实现分成两个面：**控制面**维护任务定义、SOP、版本谱系、访问权限、保留期与评测配置；**数据面**维护原始流、结构化 Trace、标签、特征与索引，两者通过 `experience_id` 与不可变 `artifact_id` 连接。关键接口是这张清单：`BeginRun` / `EndRun`、`AppendTraceEvent`、`UploadChunk`、`EmitSemanticLabel`、`AttachEvaluation`、`RegisterChangeCandidate`、`ReleaseDecision`。接口数量不多，但它们把「记录」和「判断」分开了——没有 `AttachEvaluation` 与 `ReleaseDecision`，前四个接口产出的就只是日志。

落地顺序建议按证据可信度推进，而不是按功能数量推进：

| 阶段 | 交付重点 | 验收条件 |
| --- | --- | --- |
| P0 证据闭合 | 统一 ID、时间戳、版本、原始采集与回放 | 可复现任意抽样任务的关键决策与物理过程 |
| P1 语义与持续评测 | SOP 分段、独立验证、客户口径与舰队看板 | 站点 / 机器人 / 版本切片稳定，人工抽检误差可量化 |
| P2 失败驱动优化 | 归因队列、训练片段、工具 / Harness 候选、回归集 | 失败可定位到干预层级，候选改进有冻结对照 |
| P3 自改进编排 | 多出口更新、主动采集、灰度与回滚 | 长期无干预时长与客户质量持续提升，且保护指标不退化 |

::: my-take
这套设计里我最想强调的是：**数据飞轮的转速不由采集带宽决定，而由归因与门禁决定。** 采集是整条链路上最容易扩容、也最容易假装在工作的一环——它的产出（数据量、时长、轨迹条数）随时可报，而它的价值完全取决于后面两段能不能消化。

由此有三条我认为应当先写进设计文档再谈投入的判断：

1. **失败的诊断价值必须先扣除三类伪失败。** 时钟错位、评测器口径问题与硬件漂移都会产生看起来像模型退化的现象。先修这三样，再决定是否动模型——否则你会花钱训练一个模型去修一个标定问题。
2. **没有保护集的改进不叫改进。** 任何候选变更都要能回答「它在哪些切片上更好、在哪些切片上可能更差」。只报一个综合分数的改进，无法与「换了尺子」区分。
3. **飞轮的指标不是数据量，而是单位机器人小时与工程成本换来的、通过保护集验证的能力增量。** 这个量很难测，但正因为难测，才是它值得被当成指标的原因。
:::

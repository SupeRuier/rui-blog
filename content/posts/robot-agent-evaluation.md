::: tldr
评测 Robot Agent 的困难不在选哪个指标，而在**被测对象变了**。

评测单个模型时，评测单元是一个个互相独立的任务实例，单步正确性可以相加，「准确率」是有意义的压缩。评测一个会调工具、会重规划、会失败重试的系统时，后续输入由系统自己的决策产生，单步正确性不再可加；「任务成功率」这一个数字也无法说明失败发生在哪一层。

本文因此分两章展开：**模型与能力评测**（任务定义、数据与判分接口、统一框架、结果分析），以及 **Robot Agent 调度层评测**（执行轨迹、分层归因、反馈与重规划质量）。中间用一节过渡，说明静态样本评测为什么解释不了交互系统的行为。

如果只记一句：调度层评测的核心产出不是分数，而是**归因分辨率**——能否把一次失败稳定地定位到 Planner、Harness、工具、Policy 还是环境。
:::

::: question
当被测对象从一个模型变成一个会调工具、会重规划的系统，评测到底在测什么？
:::

评测实践中，指标通常是最先被讨论、也最容易被替换的部分。真正决定一次评测有没有信息量的，是更前面的两个问题：**被测对象系统（SUT）是什么**，以及**一个评测单元（unit）是什么**。被测对象是模型权重时，评测单元是一个「输入 → 参考输出」的实例；被测对象是「Planner + Harness + 工具 + Policy」的组合时，评测单元就变成了**一条执行轨迹**，以及轨迹上的分布。下面这张图是全文的组织方式：随着被测对象从单点能力走向系统调度，评测单元依次向外扩一圈。

## 01 · 评测单元随被测对象变化

**本文采用的划分。**我把评测分成「模型与能力评测」和「调度层评测」两类，区分的依据不是被评价的东西是软件还是硬件，而是**评测单元是否包含系统自身产生的状态**。前者可以按实例独立计分，后者的输入分布依赖系统此前的决策，因此必须以轨迹为单位。

这个划分有一个实际后果：**同一个系统成功率数字，在两类评测里含义不同**。模型能力评测里的成功率是「在固定分布上取样的期望正确率」；调度层评测里的成功率是「在一批任务上，系统恰好走通的比例」，它同时包含了策略质量、工具可靠性、环境随机性和运行时长限制。把它们放在同一张表里比较，是把两种不同的量纲当成了一种。

一个容易被忽略的前置问题是**任务来源**。能力评测的任务通常来自固定数据集，可以离线复算；调度层评测的任务往往需要环境在环，环境本身是有状态的，重复运行不保证同分布。因此调度层评测在报告结果时，至少要说清三件事：任务的来源与难度分布、环境的确定性与控制方式（是否固定随机种子、是否使用真机）、以及失败是否被计入分母。缺了这三项，数字之间不可比。

## 02 · 模型与能力评测：把能力拆成可判分的任务

### 2.1 任务定义：抽象能力必须先落成实例

「世界理解」「空间推理」这类说法无法直接评测，需要先落成可判分的任务实例。STI-Bench 的做法是把「模型是否具备精确的时空世界理解」拆成一组可自动判分的问答任务，从而把抽象能力变成可复现的测量 [@1]。RoboBrain 2.0 则给出了能力、数据与训练验证之间的对应关系，把「模型应该会什么」与「用什么数据训出来」绑在一起 [@2]。

**我的判断是**，这一步最容易被做成本末倒置：先有数据集，再从数据集反推能力定义，于是「能力」退化成了「这个数据集上的分数」。更稳的顺序是先写出能力清单和每条能力的判分接口，再去找或造数据；判分接口写不出来，说明这条能力还没被定义清楚。

模型侧的具体形态不影响这套框架。OpenVLA 这类开源视觉语言动作模型 [@3] 与纯理解模型的差别在于输出空间——一个是动作 token，一个是文本——但评测时同样需要把「输出」和「判分」解耦成两个独立的部分。

### 2.2 数据与判分接口

判分器本身是可评测对象，这一点常被跳过。选择题答案可以精确匹配，但开放式输出、动作序列、规划结果通常需要规则判分或模型判分，而判分器会带来自己的误差：

- **精确匹配**：可复现，但只能覆盖答案唯一的任务；
- **规则判分**：需要先把输出解析成结构化形式，解析失败要算作失败还是算作格式错误，是一个必须显式定义的口径；
- **模型判分（LLM / VLM Judge）**：覆盖面最广，但需要单独评测判分器的一致性——同一份输出重复判分是否稳定、与人类标注的一致率是多少。如果判分器的噪声量级和被测系统之间的差距相当，这批评测就不足以支撑结论。

我在实现里沿用一条约束：**判分逻辑不进模型侧代码**。模型接入只实现一个推理接口，任务构造、结果解析和打分都在评测侧完成。好处是同一批任务换模型时，判分口径不会跟着变——否则「提升」有可能只是模型换了输出格式。

### 2.3 统一框架

当模型数量、任务数量和判分口径同时增长时，需要一层统一 runner：任务按统一 schema 描述，模型按统一接口接入，结果按统一结构落盘。规划的评测任务、能力评测任务和仿真执行任务可以接进同一个 runner，只是后者的执行环节更重。

统一框架的成本主要不在算力，而在**口径冻结**。一旦结果开始被引用，任务集的修改就必须版本化——改了题目、改了判分、改了 Prompt 模板，都是在换一把尺子。这一点与 3DGS 那类重建任务是同一类问题：**先让测量可信，再谈优化**。

### 2.4 结果分析

结果分析里最容易出错的是把不同协议的数字并列。可用的做法大致是：

1. **分层报告**，按能力维度、难度、任务来源拆开，而不是只给一个总分；
2. **给出波动范围**，尤其在小样本和高方差任务上，单点数字不足以区分两个系统；
3. **记录失败样例**，并明确失败是能力不足、格式不合规，还是任务本身有歧义；
4. **标注不可比性**，跨论文数字若任务集和判分口径不同，只作参考。

::: my-take
我认为评测框架的价值不在于把分数算出来，而在于把「模型能力」变成一个**可被证伪的接口契约**——说清输入是什么、输出必须满足什么约束、在什么条件下算通过。分数只是这个契约的执行记录。反过来，一个只能产出总分、说不清判分边界的评测，对模型迭代几乎没有指导作用。
:::

## 03 · 过渡：静态样本为什么解释不了交互系统

从能力评测走到调度层评测，中间有一个必须交代的落差：**静态样本评测的两个隐含假设，在交互系统上都不成立。**

**假设一：决策不影响后续输入的分布。** 在固定数据集上，第 i 个样本和第 i+1 个样本互不相关，模型答错第 i 题不会改变第 i+1 题的内容。交互系统里，Planner 选错工具会改变后续观测；一次失败的抓取会让物体位置变化，进而改变下一步的可达性。此时「在静态集上的准确率」描述的是模型在**数据分布**上的表现，而不是系统在**自己诱导出的状态分布**上的表现，两者可以差得很远。

**假设二：单步正确性可加。** 静态评测里，整体成绩是各样本成绩的聚合。长程任务里，成功是稀疏且尾部相关的：一步出错可能让整条轨迹归零，也可能被后续重试掩盖。因此「每步平均正确率」不能推出「任务成功率」，也不能反过来从任务成功率反推每步质量。

这两个假设失效的直接后果是，**「成功 / 失败」这个二元信号的信息量急剧下降**。SayCan 把语言模型的语言得分与机器人可供性结合，Inner Monologue 把环境反馈重新注入规划循环 [@5][@6]，SayPlan 把任务规划建立在 3D 场景图上以获得可扩展的落地能力 [@4]，Code as Policies 把动作写成可执行程序 [@7]——这些工作的共同点是把中间结构显式化。评测要跟上这类系统，也必须采集中间结构，而不只是采集结果。

## 04 · 调度层评测：执行轨迹与分层归因

### 4.1 执行轨迹：把「怎么走通的」记下来

调度层评测的原始数据单位是轨迹，而不是结果。一条可用的轨迹至少要包含：

- 任务的初始状态与目标描述；
- 每一步的子目标或决策（Planner 的中间输出）；
- 工具调用的名称、参数、返回值、耗时与错误码；
- Policy 侧的动作序列与执行结果；
- 重试、回退与取消事件，以及触发它们的原因；
- 最终状态判定，以及判定依据。

这些字段里，**耗时与错误码是工程侧最容易被省略、又最影响归因的两项**。没有超时和重试记录，一个「工具不稳定」导致的失败会看起来像是 Planner 决策错误。AutoRT 这类大规模编排工作把执行与安全约束一起纳入系统设计 [@17]，也说明编排层的可观测性和执行本身同等重要。

### 4.2 分层归因：一次失败属于哪一层

调度层评测最有价值、也最难做对的部分，是把失败定位到一层。下面五层是我在实现中采用的划分，也是本文给出的主要分析框架。

<figure class="rsi-mini"><figcaption>失败归因 · 五层，以及每层的可观测信号</figcaption><div class="rsi-mini-branches rsi-five"><div><strong>Planner</strong><span>目标分解错误、子目标顺序错误、工具选择错误、给出不可执行的目标。信号：子目标与最终目标不一致</span></div><div><strong>Harness</strong><span>上下文构造、记忆检索、接口 schema、Prompt 与重试策略。信号：同样的子目标在不同上下文下成功率显著不同</span></div><div><strong>工具 / API</strong><span>参数合法但语义不符、超时、幂等性缺失、错误码未被处理。信号：单工具离线成功率低</span></div><div><strong>Policy</strong><span>子目标正确、上下文正确，仍然执行失败。信号：给定正确子目标后成功率无法提升</span></div><div><strong>环境</strong><span>目标不可达、感知受限、非确定性、真机的物理扰动。信号：固定种子下可复现，换种子则不可</span></div></div></figure>

这个分层要能成立，每一层必须有自己的**可观测信号**，否则归因会退化成主观判断。上面每一层后面写的信号，是我认为最小可用的判据：

- Planner 的问题在于**意图层**的偏差，表现为子目标与最终目标不一致，而不是执行不出来；
- Harness 的问题具有**上下文依赖性**，同一模型、同一子目标，换一套上下文构造方式结果就变，这是最能说明问题落在 Harness 的证据；
- 工具问题可以**脱离 Agent 单独测量**，把工具拿到离线环境里跑同一批参数，成功率低就是工具的问题；
- Policy 问题的判定方式是**控制变量**：把子目标替换成人工给定的正确子目标，如果成功率没有明显提升，说明瓶颈不在调度；
- 环境问题的特征是**种子敏感性**，以及目标在当前场景下客观不可达。

「What Matters in Orchestrating Robot Policies」一类对分层 VLA Agent 的系统性研究 [@8] 是有意义的旁证：如果调度方式本身不构成独立方差，这类研究不会得到稳定的差异。同一方向上，RoboOS 用 Brain–Cerebellum 结构组织跨本体协作 [@9]，THEA、Vesta 等工作处理 Agent 的编排与层级调度 [@10][@11]，RoboHarness 关注异构 Policy 的记忆驱动编排 [@12]，VLAs-as-Tools 把 VLA 降级为被调用的工具 [@13]，ALRM、CaP-X、RPent 则分别从不同角度处理多轮生成、执行与修复的循环 [@14][@15][@16]。这些系统的架构差异，恰好对应上面五层的不同切分方式。

::: my-take
我认为调度层评测的核心指标不是任务成功率，而是**归因分辨率**：给定一批失败，能否稳定地把它们分派到层，并且不同的人、不同的时间做这件事能得到相近的结论。成功率只告诉你系统整体行不行，归因分辨率才告诉你**下一步该改哪里**。一个 60% 成功率但归因清晰的系统，比一个 75% 成功率而失败原因不可解释的系统更可迭代。
:::

### 4.3 反馈与重规划质量

只统计最终成功与否，会漏掉一个关键问题：**反馈有没有真的改变后续行为**。

一批任务在重试后成功，可能来自三种完全不同的机制——Planner 真的换了一条路径；系统重复了同样的动作、只是环境这次恰好配合；或者底层 Policy 在多次尝试中偶然成功。三者在成功率上完全一样，在系统质量上差别很大。可用的区分信号是：

- **动作序列的差异度**：重规划前后的动作序列若高度相似，重规划是名义上的；
- **反馈信息的利用率**：环境返回的错误信息是否出现在后续决策中（例如错误码触发了特定的回退分支）；
- **恢复的可复现性**：同一失败在相同条件下重复出现时，恢复路径是否稳定。
- **无效重试的代价**：重试次数与最终成功率的曲线——若曲线很快走平，多出的重试只是在消耗时间预算。

Reflexion 这类把失败转化为语言反馈并重新尝试的方法 [@18]，其效果本身就依赖于「反馈改变了后续行为」这一前提。评测如果不检验这个前提，就无法区分「反思有效」和「多试几次」。

### 4.4 两条不能越界的归因

有两类结论在调度层评测里必须避免，它们都会把评测结论变成错误的技术判断。

**第一，不能把底层 Policy 的失败归因于调度。** 如果给定正确的子目标和充足的上下文，Policy 仍然抓不起来，那么这是 Policy 层的能力问题，与 Planner 或 Harness 无关。把它记成「调度失败」，会误导系统层去做无效的 Prompt 优化或流程重构。

**第二，不能把评测服务等同于模型训练成果。** 搭建评测框架、跑通服务链路、产出规模化的评测结果，证明的是**测量基础设施**可用，不是模型能力本身。这两件事在简历和汇报里经常被合并成一句「搭建了评测体系并提升了模型效果」，但中间缺的那一步——模型是否因评测结论而真的变好——需要单独的对照实验来支撑。这一点与统一多模态模型那篇里对「已打通的任务链路」和「未完成的全量训练」的区分是同一条纪律。

## 05 · Synthesis：一份评测设计清单

把上面两章合起来，可以得到一份不依赖具体指标的检查清单。它的作用是在写评测代码之前，先把口径定下来。

| 检查项 | 要回答的问题 | 常见错误 |
| --- | --- | --- |
| 被测对象 | SUT 是模型、是「模型 + Prompt + 判分器」，还是完整系统？ | 把系统指标当成模型能力，或反过来 |
| 评测单元 | 单元是任务实例还是执行轨迹？样本之间是否独立？ | 用独立样本的统计方法处理相关轨迹 |
| 判分接口 | 判分能否复现？判分器自身是否被评测过？ | 判分逻辑混进模型侧，换模型即换口径 |
| 轨迹记录 | 是否记录中间决策、工具调用、超时与重试？ | 只存最终结果，事后无法归因 |
| 分层信号 | 五层各层是否有可观测判据？ | 归因靠印象，不同人结论不一致 |
| 重规划质量 | 反馈是否真的改变了后续行为？ | 把重试成功一律记为「恢复能力」 |
| 结果报告 | 是否给出分布、波动范围与不可比说明？ | 不同协议的数字并列比较 |
| 边界声明 | 是否区分了「测量基础设施」与「模型能力提升」？ | 把评测服务写成训练成果 |

### 开放问题

- **归因的 ground truth 从哪来。** 目前分层归因依赖人工标注与工程直觉，缺少公开数据集。若有带层级标注的失败轨迹集，归因模型本身就可以被训练和评测。
- **环境非确定性下的可复现性。** 固定种子能带来可复现性，但也会让系统过拟合到特定扰动序列；真机评测则相反。如何在这两端之间取一个可比较的口径，尚无共识。
- **长程任务的统计功效。** 任务成功率低、单次运行成本高，意味着要区分两个系统往往需要很大的样本量。评测预算本身就是设计约束。
- **持续能力变化的评测。** 对 RoboCat、Voyager 这类会跨轮次积累能力的系统 [@19][@20]，以及 RISE、Q-Planning 这类把改进建立在世界模型或离线数据上的方法 [@21][@22]，单次成绩并不说明问题——需要在同一任务分布上重复测量「能力差」，而这类重复测量目前还缺少标准做法。

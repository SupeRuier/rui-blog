::: tldr
具身系统评测的困难不在选哪个指标，而在**被测对象一直在变大**。

评测单个模型时，评测单元是一个个互相独立的任务实例，单步正确性可以相加，「准确率」是有意义的压缩。评测一个会调工具、会重规划、会失败重试的系统时，后续输入由系统自己的决策产生，单步正确性不再可加，评测单元变成**执行轨迹**。评测一台要在客户现场连续跑一个班次的机器时，评测单元再扩一级：**场地、机器人、模型与软件版本、运行时长共同决定一条数据属于谁**；此时「任务成功率」既不说明失败发生在哪一层，也不说明结果是否合格、是否需要人看护。

本文沿这条阶梯展开：**协议与数据记录**（先把口径冻结，再谈分数）、**模型与能力评测**（任务定义、判分接口、开源 benchmark 坐标）、**调度层评测**（执行轨迹、五层归因、重规划质量）、**真机与工作流评测**（production pass、质量、泛化、Recovery、干预与 MTBI）、**部署即评测**（漂移、低频故障、硬件退化、安全）与**持续改进的净提升**。

如果只记一句：随着被测对象扩大，评测的核心产出依次从「分数」变成**归因分辨率**，再变成**可归因的现场证据**——能否把一次失败稳定地定位到某一层，并说清这个结论只在什么条件下成立。
:::

::: question
当评测单元从一道题、一条轨迹，变成一台机器的一个班次，「通过」的定义要怎么重写？
:::

评测实践中，指标通常是最先被讨论、也最容易被替换的部分。真正决定一次评测有没有信息量的，是更前面的两个问题：**被测对象系统（SUT）是什么**，以及**一个评测单元（unit）是什么**。被测对象是模型权重时，评测单元是一个「输入 → 参考输出」的实例；被测对象是「Planner + Harness + 工具 + Policy」的组合时，评测单元变成一条执行轨迹；被测对象是一台在现场连续运行的机器时，评测单元进一步变成**带场地与版本标签的部署单元**。

### 1.1 两类评测：单元里是否包含系统自己产生的状态

**本文采用的划分。**我把评测分成「模型与能力评测」和「系统层评测」两类，区分的依据不是被评价的东西是软件还是硬件，而是**评测单元是否包含系统自身产生的状态**。前者可以按实例独立计分，后者的输入分布依赖系统此前的决策，因此必须以轨迹或更长的时间窗为单位。

这个划分有一个实际后果：**同一个成功率数字，在两类评测里含义不同**。模型能力评测里的成功率是「在固定分布上取样的期望正确率」；系统层评测里的成功率是「在一批任务上，系统恰好走通的比例」，它同时包含了策略质量、工具可靠性、环境随机性和运行时长限制。把它们放在同一张表里比较，是把两种不同的量纲当成了一种。

一个容易被忽略的前置问题是**任务来源**。能力评测的任务通常来自固定数据集，可以离线复算；系统层评测的任务往往需要环境在环，环境本身是有状态的，重复运行不保证同分布；到了部署现场，连「同一批任务」都不成立——任务构成随订单、班次和客户现场变化。因此报告结果时至少要说清三件事：任务的来源与难度分布、环境的确定性与控制方式（是否固定随机种子、是否使用真机）、以及失败是否被计入分母。缺了这三项，数字之间不可比。

### 1.2 粒度阶梯：组件、原子任务、复合任务、工作流、部署单元

比「软件还是硬件」更好用的坐标是**粒度**：

- **组件**：感知与状态估计、决策与 Orchestrator、策略与验证器、控制器与运行时。组件评测回答的是「哪个环节限制了整机表现」。
- **原子任务**：有明确起点和物理终态的单步任务，例如「把毛巾放进烘干机」。
- **复合任务**：带顺序依赖的多个原子任务，例如「取、洗、烘、叠、上架」。
- **工作流**：在复合任务之上还包括分支、并行资源、异常处理和人工接管的完整业务流程。
- **部署单元**：由场地、机器人、模型与软件版本、运行时间共同确定的运行实例——同一套模型部署到两个门店，就是两个部署单元。

泛化、Recovery、硬件与运行时可靠性、Safety 不属于其中某一级，而是**跨粒度考察的属性**；持续自我改进则比较同一系统在多个版本之间是否真的变好。后面几章按这个阶梯逐级展开。

### 1.3 三条贯穿全文的主线

粒度阶梯提供坐标，真正的判断靠三条主线：

1. **task success 与 production pass 是两个口径。** 前者确认目标状态达成，后者在目标状态之外加入质量、时限和损伤约束。一个能完成任务的系统，可能长期产不出「可交付」的结果。
2. **首次成功、自动恢复后成功、人工介入后完成，对应三种不同的自主性。** 把它们混成一个成功率，等于把「能自己干」和「有人扶着也能干」记成同一件事。
3. **模型故障与系统故障要分开。** 客户感受到的是整机是否完成工作，因此硬件和运行时故障必须计入最终结果；但改进需要把故障定位到感知、规划、策略、控制、运行时、硬件或环境，否则修复方向只能靠猜。

### 1.4 证据阶梯：后一类证据不会自动覆盖前一类

从证据来源看，评测依次使用**开源 benchmark → 受控真机试验 → 连续工作流试验 → 现场部署数据**，可比性、物理有效性、长程自主性与跨时间稳定性分别由这四档提供。

关键约束是：**后一类证据不会自动覆盖前一类**。现场总指标最容易反映真实价值，却也最难定位故障——它告诉你「这个月产出掉了」，不告诉你掉在哪一步；仍需要组件诊断和受控试验来归因。反过来，benchmark 分数高也不能推出现场可用。四档证据是并联关系，不是串联升级关系。

## 02 · 统一评测协议与数据记录

口径必须先冻结，再谈分数。一旦结果开始被引用，改题目、改判分、改预处理都等于换了一把尺子。我在实现里看到的规律是：**统一框架的成本主要不在算力，而在口径冻结**。

| 项目 | 执行规则 | 产出及用途 |
| --- | --- | --- |
| 任务卡 | 写明起点、目标状态、物体范围、允许动作、超时、质量标准、危险边界及重置方式 | 形成可复现试验；防止临场改口径 |
| 分组 | 训练／调参／封闭测试分离；按物体、摆位、场地、光照、机器人、人员分层抽样 | 可比较的已见与未见表现 |
| 试验记录 | 保存视频、传感器、动作、目标轨迹、模型版本、控制器与固件版本、站点、时间、干预与故障码 | 支持复核和归因 |
| 评分 | 独立结果判定；模糊案例双人复核；记录首次成功、恢复后成功、质量、耗时及危险事件 | 减少自评偏差 |
| 统计 | 报告分子 / 分母、95% 区间和各切片；稀有故障按运行小时或作业量报告 | 避免小样本百分比误导 |

建议的最小数据单元是：`trial_id`、`task_id`、`scenario_id`、`site_id`、`robot_id`、`checkpoint_id`、软硬件版本、起止时间、`outcome`、`quality`、`intervention_type`、`failure_owner` 和证据链接。指标命名与事件分类在首轮评测前冻结；发现新类别可以增补，但历史记录要能重算。

这里有两处容易被省略、又最影响归因的字段：**干预类型**与**故障归属**。没有它们，一次「工具不稳定」导致的失败看起来会像 Planner 决策错误，一次磨损夹爪导致的失败看起来会像模型退化。

## 03 · 模型与能力评测：把能力拆成可判分的任务

### 3.1 任务定义：抽象能力必须先落成实例

「世界理解」「空间推理」这类说法无法直接评测，需要先落成可判分的任务实例。STI-Bench 的做法是把「模型是否具备精确的时空世界理解」拆成一组可自动判分的问答任务，从而把抽象能力变成可复现的测量 [@1]。RoboBrain 2.0 则给出了能力、数据与训练验证之间的对应关系，把「模型应该会什么」与「用什么数据训出来」绑在一起 [@2]。

**我的判断是**，这一步最容易被做成本末倒置：先有数据集，再从数据集反推能力定义，于是「能力」退化成了「这个数据集上的分数」。更稳的顺序是先写出能力清单和每条能力的判分接口，再去找或造数据；判分接口写不出来，说明这条能力还没被定义清楚。

模型侧的具体形态不影响这套框架。OpenVLA 这类开源视觉语言动作模型 [@3] 与纯理解模型的差别在于输出空间——一个是动作 token，一个是文本——但评测时同样需要把「输出」和「判分」解耦成两个独立的部分。

### 3.2 数据与判分接口

判分器本身是可评测对象，这一点常被跳过。选择题答案可以精确匹配，但开放式输出、动作序列、规划结果通常需要规则判分或模型判分，而判分器会带来自己的误差：

- **精确匹配**：可复现，但只能覆盖答案唯一的任务；
- **规则判分**：需要先把输出解析成结构化形式，解析失败要算作失败还是算作格式错误，是一个必须显式定义的口径；
- **模型判分（LLM / VLM Judge）**：覆盖面最广，但需要单独评测判分器的一致性——同一份输出重复判分是否稳定、与人类标注的一致率是多少。如果判分器的噪声量级和被测系统之间的差距相当，这批评测就不足以支撑结论。

我在实现里沿用一条约束：**判分逻辑不进模型侧代码**。模型接入只实现一个推理接口，任务构造、结果解析和打分都在评测侧完成。好处是同一批任务换模型时，判分口径不会跟着变——否则「提升」有可能只是模型换了输出格式。

这套纪律在真机和部署层同样成立，而且更贵：真机试验里的「质量是否达标」通常需要人工或独立视觉判定，**不能让执行系统自己给自己评分**。

### 3.3 统一框架

当模型数量、任务数量和判分口径同时增长时，需要一层统一 runner：任务按统一 schema 描述，模型按统一接口接入，结果按统一结构落盘。规划的评测任务、能力评测任务和仿真执行任务可以接进同一个 runner，只是后者的执行环节更重。

统一框架的另一个作用是把**口径变更**变成可审计事件。任务集的修改必须版本化——改了题目、改了判分、改了 Prompt 模板，都是在换一把尺子。这一点与 3DGS 那类重建任务是同一类问题：**先让测量可信，再谈优化**。

### 3.4 结果分析

结果分析里最容易出错的是把不同协议的数字并列。可用的做法大致是：

1. **分层报告**，按能力维度、难度、任务来源拆开，而不是只给一个总分；
2. **给出波动范围**，尤其在小样本和高方差任务上，单点数字不足以区分两个系统；
3. **记录失败样例**，并明确失败是能力不足、格式不合规，还是任务本身有歧义；
4. **标注不可比性**，跨论文数字若任务集和判分口径不同，只作参考。

::: my-take
我认为评测框架的价值不在于把分数算出来，而在于把「模型能力」变成一个**可被证伪的接口契约**——说清输入是什么、输出必须满足什么约束、在什么条件下算通过。分数只是这个契约的执行记录。反过来，一个只能产出总分、说不清判分边界的评测，对模型迭代几乎没有指导作用。
:::

### 3.5 开源 benchmark：可比较的坐标，不是能力结论

开源 benchmark 解决的是「和别人比」的问题，它提供标准化任务、迁移、扰动和长程能力的公共坐标：

| 基准 | 评什么 | 怎么评 | 读出什么 |
| --- | --- | --- | --- |
| LIBERO [@23] | 操作与知识迁移 | 按官方任务、初始状态和成功判据运行；明确 zero-shot 或微调设置 | 各 suite 成功率及迁移 / 遗忘 |
| LIBERO-Plus [@24] | 鲁棒性 | 固定任务目标，逐项改变物体布局、相机、初始姿态、语言、光照、背景、噪声 | 各扰动强度下的性能曲线 |
| CALVIN [@25] | 长序列语言指令执行 | 按官方长序列协议连续执行语言子任务 | 序列成功长度及各位置成功率 |
| RoboCasa [@26] | 家居操作覆盖 | 采用对应版本官方任务和场景切分 | 技能 / 场景 / 复合任务成功率 |
| BEHAVIOR-1K [@27] | 复杂场景迁移 | 选择与业务相近的任务，遵守官方可观测量与重置规则 | 目标谓词完成度、耗时和路径代价 |

执行规则上，我会保留**一个长期稳定的主基准加一个与业务相关的补充基准**，公开报告写清版本、观测模态、动作空间、训练数据、重试次数和成功判定。

benchmark 最容易被误用成能力结论。LIBERO-Plus 按官方摘要报告：在七个维度的受控扰动下，十个当时的先进模型成功率从超过 95% 掉到 30% 以下——**基准分数高不等于能力稳**，只说明它在基准设定的那个分布上成立 [@24]。这也解释了为什么基准只能用于筛选和回归：它是坐标，不是放行依据。

## 04 · 过渡：静态样本为什么解释不了交互系统

从能力评测走到系统层评测，中间有一个必须交代的落差：**静态样本评测的两个隐含假设，在交互系统上都不成立。**

**假设一：决策不影响后续输入的分布。** 在固定数据集上，第 i 个样本和第 i+1 个样本互不相关，模型答错第 i 题不会改变第 i+1 题的内容。交互系统里，Planner 选错工具会改变后续观测；一次失败的抓取会让物体位置变化，进而改变下一步的可达性。此时「在静态集上的准确率」描述的是模型在**数据分布**上的表现，而不是系统在**自己诱导出的状态分布**上的表现，两者可以差得很远。

**假设二：单步正确性可加。** 静态评测里，整体成绩是各样本成绩的聚合。长程任务里，成功是稀疏且尾部相关的：一步出错可能让整条轨迹归零，也可能被后续重试掩盖。因此「每步平均正确率」不能推出「任务成功率」，也不能反过来从任务成功率反推每步质量。

这两个假设失效的直接后果是，**「成功 / 失败」这个二元信号的信息量急剧下降**。SayCan 把语言模型的语言得分与机器人可供性结合，Inner Monologue 把环境反馈重新注入规划循环 [@5][@6]，SayPlan 把任务规划建立在 3D 场景图上以获得可扩展的落地能力 [@4]，Code as Policies 把动作写成可执行程序 [@7]——这些工作的共同点是把中间结构显式化。评测要跟上这类系统，也必须采集中间结构，而不只是采集结果。

到真机和部署层，落差还要再大一级：**连「同一分布」都不保证**。站点的物料、光照、布局和人员会变，硬件会磨损，任务的构成随订单变化。现场数据因此只能是**观测性证据**——它能提出假设，不能单独证明因果；因果要靠受控试验。这两类证据的配合方式，是第七章和第八章的主题。

## 05 · 调度层评测：执行轨迹与分层归因

### 5.1 执行轨迹：把「怎么走通的」记下来

调度层评测的原始数据单位是轨迹，而不是结果。一条可用的轨迹至少要包含：

- 任务的初始状态与目标描述；
- 每一步的子目标或决策（Planner 的中间输出）；
- 工具调用的名称、参数、返回值、耗时与错误码；
- Policy 侧的动作序列与执行结果；
- 重试、回退与取消事件，以及触发它们的原因；
- 最终状态判定，以及判定依据。

这些字段里，**耗时与错误码是工程侧最容易被省略、又最影响归因的两项**。没有超时和重试记录，一个「工具不稳定」导致的失败会看起来像是 Planner 决策错误。AutoRT 这类大规模编排工作把执行与安全约束一起纳入系统设计 [@17]，也说明编排层的可观测性和执行本身同等重要。

### 5.2 分层归因：一次失败属于哪一层

调度层评测最有价值、也最难做对的部分，是把失败定位到一层。下面五层是我在实现中采用的划分，也是本文给出的主要分析框架。

<figure class="rsi-mini"><figcaption>失败归因 · 五层，以及每层的可观测信号</figcaption><div class="rsi-mini-branches rsi-five"><div><strong>Planner</strong><span>目标分解错误、子目标顺序错误、工具选择错误、给出不可执行的目标。信号：子目标与最终目标不一致</span></div><div><strong>Harness</strong><span>上下文构造、记忆检索、接口 schema、Prompt 与重试策略。信号：同样的子目标在不同上下文下成功率显著不同</span></div><div><strong>工具 / API</strong><span>参数合法但语义不符、超时、幂等性缺失、错误码未被处理。信号：单工具离线成功率低</span></div><div><strong>Policy</strong><span>子目标正确、上下文正确，仍然执行失败。信号：给定正确子目标后成功率无法提升</span></div><div><strong>环境</strong><span>目标不可达、感知受限、非确定性、真机的物理扰动。信号：固定种子下可复现，换种子则不可</span></div></div></figure>

这个分层要能成立，每一层必须有自己的**可观测信号**，否则归因会退化成主观判断。上面每一层后面写的信号，是我认为最小可用的判据：

- Planner 的问题在于**意图层**的偏差，表现为子目标与最终目标不一致，而不是执行不出来；
- Harness 的问题具有**上下文依赖性**，同一模型、同一子目标，换一套上下文构造方式结果就变，这是最能说明问题落在 Harness 的证据；
- 工具问题可以**脱离 Agent 单独测量**，把工具拿到离线环境里跑同一批参数，成功率低就是工具的问题；
- Policy 问题的判定方式是**控制变量**：把子目标替换成人工给定的正确子目标，如果成功率没有明显提升，说明瓶颈不在调度；
- 环境问题的特征是**种子敏感性**，以及目标在当前场景下客观不可达。

「What Matters in Orchestrating Robot Policies」一类对分层 VLA Agent 的系统性研究 [@8] 是有意义的旁证：如果调度方式本身不构成独立方差，这类研究不会得到稳定的差异。同一方向上，RoboOS 用 Brain–Cerebellum 结构组织跨本体协作 [@9]，THEA、Vesta 等工作处理 Agent 的编排与层级调度 [@10][@11]，RoboHarness 关注异构 Policy 的记忆驱动编排 [@12]，VLAs-as-Tools 把 VLA 降级为被调用的工具 [@13]，ALRM、CaP-X、RPent 则分别从不同角度处理多轮生成、执行与修复的循环 [@14][@15][@16]。这些系统的架构差异，恰好对应上面五层的不同切分方式。

::: my-take
我认为调度层评测的核心指标不是任务成功率，而是**归因分辨率**：给定一批失败，能否稳定地把它们分派到层，并且不同的人、不同的时间做这件事能得到相近的结论。成功率只告诉你系统整体行不行，归因分辨率才告诉你**下一步该改哪里**。一个 60% 成功率但归因清晰的系统，比一个 75% 成功率而失败原因不可解释的系统更可迭代。
:::

### 5.3 反馈与重规划质量

只统计最终成功与否，会漏掉一个关键问题：**反馈有没有真的改变后续行为**。

一批任务在重试后成功，可能来自三种完全不同的机制——Planner 真的换了一条路径；系统重复了同样的动作、只是环境这次恰好配合；或者底层 Policy 在多次尝试中偶然成功。三者在成功率上完全一样，在系统质量上差别很大。可用的区分信号是：

- **动作序列的差异度**：重规划前后的动作序列若高度相似，重规划是名义上的；
- **反馈信息的利用率**：环境返回的错误信息是否出现在后续决策中（例如错误码触发了特定的回退分支）；
- **恢复的可复现性**：同一失败在相同条件下重复出现时，恢复路径是否稳定；
- **无效重试的代价**：重试次数与最终成功率的曲线——若曲线很快走平，多出的重试只是在消耗时间预算。

Reflexion 这类把失败转化为语言反馈并重新尝试的方法 [@18]，其效果本身就依赖于「反馈改变了后续行为」这一前提。评测如果不检验这个前提，就无法区分「反思有效」和「多试几次」。

我在 6.1 会回到这个区分：在真机上，**「重试成功算不算成功」取决于你在回答哪个问题**。生产口径必须计入恢复后的成功，否则数字与客户体验矛盾；诊断口径必须把它拆出来，否则无法判断系统是真的会恢复，还是运气好。

### 5.4 两条不能越界的归因

有两类结论在调度层评测里必须避免，它们都会把评测结论变成错误的技术判断。

**第一，不能把底层 Policy 的失败归因于调度。** 如果给定正确的子目标和充足的上下文，Policy 仍然抓不起来，那么这是 Policy 层的能力问题，与 Planner 或 Harness 无关。把它记成「调度失败」，会误导系统层去做无效的 Prompt 优化或流程重构。

**第二，不能把评测服务等同于模型训练成果。** 搭建评测框架、跑通服务链路、产出规模化的评测结果，证明的是**测量基础设施**可用，不是模型能力本身。这两件事在简历和汇报里经常被合并成一句「搭建了评测体系并提升了模型效果」，但中间缺的那一步——模型是否因评测结论而真的变好——需要单独的对照实验来支撑。这一点与统一多模态模型那篇里对「已打通的任务链路」和「未完成的全量训练」的区分是同一条纪律。

### 5.5 从调度层到整机：归属范围的扩展

调度层五层是 Agent 系统内部的划分；一旦评测对象变成整机，失败归属要向下补齐四个类别，并且**允许一次失败同时属于多类**：

- **感知与状态估计**：标注关键物体、位置、机器状态及可操作性，覆盖遮挡和光照；看状态准确率、漏检、误检、校准误差。
- **控制器与运行时**：目标轨迹回放、负载与网络故障注入；看误差、振荡、超调、控制与推理延迟、超时率。控制器评测不能只看误差均值——均值相近的两套控制，振荡、超调和接触过程可能完全不同，物理结果也完全不同。
- **硬件**：温度、电流、电压、编码器、夹爪与传感器漂移，班前自检与故障复盘；看可用率、故障间隔、校准漂移、维修时间。
- **环境与标注**：现场物料、光照、布局变化，以及标注本身的错误。

这个扩展带来一个必须写进协议的规则：**失败归属是一个多标签字段，不是一个单选**。Dyna 的部署报告里有一个很好的例子——某个门店的产出下降，最初在系统日志里看不出原因，自动标注把失败集中到 SOP 第一步的「漏抓」，而根因是**夹爪磨损**。「磨损的夹爪和糟糕的策略在 episode 里长得一样」，标注能定位到哪一步、哪一类，但区分二者是另一个问题，需要硬件遥测做对照 [@29]。如果归因字段只能填一个值，这个案例就会被记成模型退化。

## 06 · 真机与工作流层评测

调度层评测能回答「系统在哪一层出问题」，但回答不了客户真正关心的三个问题：**结果合不合格、条件变了还行不行、要不要人看着**。这三件事只有在真机和连续运行里才能测。

### 6.1 原子任务：task success 与 production pass 是两个口径

在真机上，任务成功只确认「目标状态达成」。**production pass** 在此之上加入质量、时限和损伤约束：把毛巾放进烘干机是 task success；把毛巾以可交付的姿态、在节拍内、不损伤机器和衣物地放进烘干机，才是 production pass。

Dyna 的公开数据提供了一个可以看清两者差别的例子：其 Dyna-1 在折叠任务上有 75% 的折叠达到「上桌标准」，Dyna-2 把节拍从每小时约 35 条提高到 95 条，同时把达标率提到 93%，折算约 1,590 条 / 天，而客户需求是 18 小时班次内 1,500 条 [@29]。这里的关键不是数字本身，而是**速度与质量同时在约束里**：只报「成功率」的话，这三项约束一件都体现不出来。这些数字来自厂商官方报告，未公开完整评测协议与试验次数，只能作为量级与口径示例。

试验口径也要在任务卡里锁定：首次试验用「无人工、无重置、无隐藏预处理」；恢复和人工接管另列，不混进同一个成功率。样本量按目标精度预先确定，少样本阶段只作探索性结果。

### 6.2 质量、效率与成本

从「能完成」到「能交付」，需要把三组量放进同一张表：

- **通过类**：首次成功率、production pass 率、质量分数——若一个任务有多项质量条件，硬性通过率对应交付，连续质量分用于分析改进幅度；
- **效率类**：合格件 / 小时、单位时间合格产出、能耗；
- **代价类**：返工率、损耗、碰撞与损伤、人工分钟 / 单位产出。

这一层的常见错误是只报通过类，然后在商业决策里被效率类否决。质量与成功也需要分别定义：「放到了目标位置」可以是任务成功，但放置姿态、材料损伤或整理效果可能达不到验收要求。

### 6.3 泛化与扰动：一次只改一类因素

泛化的评测设计原则是**控制变量**：一次只改变一类因素，再做组合变化；同时保留未见过的物体、场地和指令作为封闭测试集。

- **条件泛化**：物体、摆位、光照、背景、指令表述；
- **跨本体 / 跨设备**：在不同机器人和不同标定状态下复用同一任务卡，并**记录适配投入**——适配成本是复制部署难度的直接指标；
- **跨场景**：换场地、换站点。

报告时除了各条件成功率，还要给出**相对下降**与**最差组表现**。平均分下降 10 个点与某一组从 90% 掉到 20%，对部署的含义完全不同。LIBERO-Plus 在仿真侧给出的七维扰动协议 [@24]，可以直接作为真机扰动矩阵的设计参照。

### 6.4 Recovery：发现、处置、回到有效状态

Recovery 不是一个成功率，而至少包含三个环节：**系统是否发现偏差、是否选择正确处置、处置后是否回到有效状态**。只统计「最终做成」会同时遗漏漏检、误报和不必要的重复尝试。

| 评什么 | 怎么评 | 读出什么 |
| --- | --- | --- |
| 技能内恢复 | 在安全范围注入抓取滑脱、目标偏移、物体掉落或双件等故障 | 检测率、自动恢复率、恢复时长、二次损伤 |
| 跨步骤恢复 | 在复合任务中注入步骤未完成、资源不可用或前序结果不合格 | 重试 / 替代 / 重规划正确率、最终完成率 |
| 恢复代价 | 比较干净试验与扰动试验，统计额外动作、时间与能耗 | 恢复收益与成本、失败后的风险 |
| 误报与漏报 | 混入无故障对照，审计自动停止与继续执行 | 误停率、危险漏检率 |

两件事必须分开：**技能内部的恢复与工作流级恢复**。抓取滑脱后的重新抓取可以由 Policy 完成；某台设备不可用时改做其他任务，则需要工作流调度。两者由不同模块实现，对训练数据和评测样本的要求也不同。

另一件事是**口径**：如果扰动是注入的，要明确区分自发失败、注入失败与人为干预；一次失败允许多因并存，但每个失败至少归入感知、规划、策略、控制、硬件、环境或标注之一。受控扰动必须通过安全审查，并在同一初始状态下建立干净试验与扰动试验的**配对比较**，否则恢复带来的额外时间、动作数、能耗和损伤风险无法估计。

### 6.5 复合任务与工作流：步骤、终态、干预

长流程对局部错误极其敏感。对固定的、全部必需且相互独立的 N 个步骤，如果每步成功概率都是 p，完整流程的理论成功概率是 `p^N`——这能说明长链条为什么脆弱，但它**不是工作流的实测完成率**。真实工作流有分支、重复、自动恢复、共享环境状态和相关故障；一次设备故障还可能同时影响多个步骤。

Dyna-2.1 的报告里用这个式子做过一个示意：把每个子任务的可靠率都设成 95%，一个约 79 步的洗衣流程单周期「无人帮忙做完」的概率只有约 2% [@28]。需要强调，**这个数字在该报告里被明确标注为示意值（由页面上的滑块设定），不是实测结果**。它的价值只在于说明一件事：长流程里「每步都还不错」和「整条流程能自己走完」是两个量级的事。

因此长程评测要直接运行完整流程，并拆解三层结果：

<figure class="rsi-mini"><figcaption>工作流结果必须拆成三层，混报会互相掩盖</figcaption><div class="rsi-mini-branches"><div><strong>步骤完成率</strong><span>说明局部能力：哪一步最容易失败、失败后能否继续</span></div><div><strong>流程终态</strong><span>说明业务结果：整条流程是否在时限内产出合格结果</span></div><div><strong>人工干预</strong><span>说明人力代价：谁在什么时候介入、介入多久、恢复方式是什么</span></div></div></figure>

只有流程终态成功，仍可能掩盖频繁人工帮助。对每次干预要记录触发点、原因、持续时间和恢复方式，才能解释看护需求的变化。

### 6.6 MTBI、干预次数与无干预时长不是同一个指标

**MTBI（mean time between interventions）** 可定义为总自主运行时间除以必要人工干预次数，适合比较看护需求，但它不能单独描述风险分布。两套系统的 MTBI 相同，一套可能定期在固定环节请求协助，另一套可能偶发难以预测的严重卡死——前者可排班，后者不可。

因此还要同时给出：**每班干预次数、P50 / P90 无干预时长、干预严重度和人工处理时间**。零干预样本要注明实际观察时长——观察了两小时没有干预，不等于已经证明可以无干预工作一整天；这种情形下应报告总观测时长，而不是把它写成「无限大」。

最后是分类问题：**流程设计里规定的人工操作，与机器人无法继续而发生的干预，不能混算**。客户规定危险操作必须人工确认，那是流程设计；任务失败后由人解救，那是能力不足。两者对产品设计都有意义，但对「自主性」的含义相反。

## 07 · 部署即评测

### 7.1 一小时试验抓不到什么

在实验室里评测有很便宜的答案：跑几十次试验，让人看着打分。当模型离生产级还很远时，这足够了——你要判断的是「这东西到底行不行」。问题在于它**混淆了什么、又漏掉了什么**。

Dyna 的部署报告把这件事讲得很直接：内部 benchmark 能说明模型在变好，但不能说明它几个月后是否还在客户现场正常工作。一小时的测试能抓到完全不工作的模型，**抓不到每两百次失败一次、一周内逐渐退化、或在这台机器人上正常而旁边那台很差的模型**；它也完全说明不了站点本身——工位会被挪动，光照会变，供应商会换材料。「基准是静止的，站点不是」[@29]。这段是厂商的立场陈述，但它描述的失效模式与我上面 6.1–6.6 的口径设计指向同一处：**实验室试验与现场表现之间的差距，不是靠加样本量补上的，而是靠换测量方式**。

### 7.2 持续测量：把每个 episode 变成证据

「部署即评测」的含义不是「多跑数据」，而是**把评测变成一项基础设施**：每一次机器人产生的 episode 都被记录下来，并按客户自己的质量标准判分。这要求先在工程上解决四件事：

1. **把完整工作日取下来**：相机流、机器人状态、控制指令、应用事件与硬件遥测，带足以重建时间对齐的时序信息；
2. **在采集端保住证据**：运行时持续维护一个固定大小的近期活动窗口，当系统或操作员检测到异常时，把相关窗口提升为可回放的 episode，保留事发前的来龙去脉与事后一小段；上传异步进行，本地副本在远端校验通过后才删除；
3. **给 episode 打上语义标签**：按任务的 SOP 把一次运行切成步骤，标注每步的起止、是否成功、失败模式——注意这里的关键是**标注**，因为在系统日志里，「完成了一次操作」和「这次操作合格」是两件事；
4. **把标签变成可查询的维度**：按步骤、结果、失败模式、站点、硬件状态和 checkpoint 检索，让聚合结果始终能一键跳回原始证据。

Dyna 报告里给出的规模是每天超过 1 TB 原始数据，并采用「自动标注覆盖全量 + 人工复核集中在高信息量切片（新任务、稀有或模糊结果、低置信输出、疑似回退，以及用于测量标注质量本身的抽样）」的混合流程 [@29]。这印证了一个我觉得很重要的判断：**在部署层，评测的主要成本不是算分，而是把非结构化的运行记录变成可判分、可检索的结构**。

### 7.3 分层与分母：现场比较的可归因性

现场部署产生大量真实数据，但**大样本本身不保证可解释**。某一周通过率上升，可能来自模型改进，也可能是任务组合更简单；某台机器人表现较差，可能是夹爪磨损或相机标定偏移。现场比较至少要按**任务、场地、机器人、模型 / 控制器版本和时间**分层，并记录环境与硬件变化。

对低频故障，分母要用**运行小时、作业次数或操作次数**，而不是只报绝对故障数。「这个月有 12 次卡死」在不同作业量下含义完全不同。对版本更新，可用同场地时段对照、配对任务或小范围灰度减少环境差异；如果条件无法严格匹配，结论应明确其**观察性**性质。

硬件退化提供了一个特别值得单列的场景：机械部件是逐渐退化的，而从外部看，退化很容易被误认为模型回退或软件变更。报告里的做法是给每个部件建立相对自身基线的退化指数，并结合定期标定与退化检查，在「磨损开始限制模型表现」之前报警 [@29]。这里的技术要点不在于指标多精巧，而在于**先把模型变量与硬件变量分开记录**，否则两者互相污染，任何趋势分析都不可信。

### 7.4 版本对照与回滚

部署评测的最终用途是决定「要不要扩大部署」。因此每次版本更换都应产出对照报告：新旧版本在质量、吞吐、干预和故障上的净提升，以及**回归清单**。做法上有三档，成本与可信度递增：

- **同场地分时段对照**：成本最低，受时段差异影响；
- **配对任务或影子评估**：同一批任务并行跑，或让新版本在旁路运行；
- **分站点 / 分机器人受控对照**：最接近因果，但运营成本最高。

无论用哪一档，都要预设**预警与回滚条件**，并明确阈值来自哪里——阈值由目标场景和客户验收标准确定，不由评测方单方面设定。

### 7.5 硬件、运行时与安全的位置

整机结果必须把硬件和运行时故障算进去，因为客户看到的是「系统有没有完成工作」；技术归因则要把它们拆开。

- **运行时可靠性**：压力运行与故障注入，覆盖断网、超时、进程重启、时间同步；看调用成功率、延迟分位数、恢复时间。
- **物理安全**：定义人机距离、力 / 速度、禁区、急停与异常停止，在安全场地验证；看越界、碰撞、急停事件与近失事件。
- **数据与操作安全**：权限、日志完整性、远程接管与人工复位流程；看审计通过率与事件闭环时间。

**安全指标与任务成功率的统计性质不同。** 平均成功率可以容忍一定数量的一般失败，严重危险事件却可能直接改变场景的可部署性。因此安全结果**不并入平均分**：应单列危险事件、近失事件、急停、越界及物品损伤，并保留触发前后的系统记录。任何严重危险事件都暂停对应场景的放行，完成根因分析、修复、复测后再恢复。安全边界既是评测结果，也是试验设计的前提。

::: my-take
我认为在部署层，「评测」与「运营」的边界必须刻意保留。把现场仪表盘上的通过率直接当成评测结论，是这一层最典型的错误：它既是观察性数据、又混着任务构成和硬件变化，还常常由执行系统自己上报。部署数据的长处是覆盖面——它能发现实验室根本覆盖不了的低频事件和长期退化；它的短处是**只能提出假设**。把「部署提出假设、受控试验验证原因」这条回路显式写下来，部署评测才不只是监控。
:::

## 08 · 持续改进：净提升要能被证明

### 8.1 失败发现与数据闭环

部署失败可以转化为新数据，但**「收集更多数据」不等于系统已经改进**。有效的闭环是：按失败类型采样并复核，记录新增数据来源、标签和修复假设；用「高价值失败覆盖率」和「标注一致性」判断这一轮收集是否真的覆盖了要紧的失败。

这里有一个与第六章呼应的细节：episode 能定位失败发生在哪一步、属于哪一类，但**通常不能直接给出根因**（磨损的夹爪与糟糕的策略在记录里长得一样）。因此数据闭环的产出不是一个结论，而是一组**可检验的修复假设**——每条假设都要写清它预期改善哪类失败、可能影响哪些旧能力。

这条链路在工程上具体怎么组织——统一 Experience 单元、Raw / Semantic / Derived 三层、失败归因、多出口候选变更与发布门禁——见[具身 Agent 数据飞轮：从部署记录到能力演进](embodied-data-flywheel.html)。

### 8.2 净提升的三个分量

每次版本更新都应同时报告三个分量：

1. **目标改善**：在固定的封闭测试集与新增场景集上，用配对试验比较新旧版本的成功、质量和干预；
2. **遗忘与回归**：重跑历史高频、高风险任务以及开源基准的关键切片，产出退化任务清单与最差组变化；
3. **单位数据收益**：改善量与投入的数据 / 算力之比——这决定了这条路是否值得再走一遍。

只有第一项为正、第二项为空、第三项可以接受，才叫净提升。只报第一项是这一层最常见的偏差，因为后两项需要额外成本，而且结果通常不好看。

### 8.3 上线闭环

灰度与小范围部署是闭环的最后一环：监测漂移、异常和回滚触发，用线上净收益、回滚率和问题关闭时间判断是否推广。这一环也包含了 §5.4 提到的那条纪律的反面：**搭建评测与数据管线本身是「测量基础设施」的成果，不是模型能力的成果**；两者要分开陈述，只能用对照实验把后者证出来。

在这条路径上，评价对象不是某一个 checkpoint，而是**同一任务分布上跨版本的能力差**。这与 Agent RSI 那一篇讨论的问题相接：单次成绩不说明问题，重复测量「能力差」才是。

一个不可妥协的规则：**封闭测试集的轨迹不能用于调参后仍被称为独立测试**。这是所有分层评测的地基——口径一旦被优化目标污染，后面所有指标都失去了含义。

## 09 · Synthesis：分层矩阵、清单与实施

### 9.1 一张分层矩阵

把前面几章合成一张表。它不能替代具体设计，作用是在写评测代码之前先把「这一层到底测什么、拿什么当证据」对齐。

| 层级 | 被测对象 / 评测单元 | 关键指标 | 主要证据 | 常见误读 |
| --- | --- | --- | --- | --- |
| 组件 | 单个环节；离线或受控闭环 | 判定错误率、动作成功与进度、控制误差与延迟、故障码 | 标注数据、轨迹回放、故障注入 | 用整机成功率代替组件诊断 |
| 开源 benchmark | 官方任务集与判据 | 各 suite 成功率、扰动强度曲线、迁移与遗忘 | 官方协议复现 | 把基准分数当成真实能力 |
| 真机原子任务 | 标准起点上的一次无人工试验 | 首次成功率、production pass、时长分布、质量缺陷 | 受控真机试验 | 用 task success 代替可交付 |
| 泛化与 Recovery | 单因素 / 组合变化、注入故障 | 各条件成功率与最差组、检测率、恢复率、恢复代价 | 配对试验、受控扰动 | 把「重试成功」一律记为恢复能力 |
| 复合任务与工作流 | 一个班次内的连续运行 | 步骤完成率、流程终态、干预次数 / 小时、MTBI、无干预时长 | 连续工作流试验 | 只报终态成功率，隐藏人工干预 |
| 部署单元 | 场地 × 机器人 × 版本 × 运行时间 | 合格产出、吞吐、人工分钟 / 单位、漂移、故障率 / 千小时 | 现场部署数据 | 把观察性相关当成因果结论 |
| 跨版本 | 同一任务分布上的能力差 | 净提升、回归清单、单位数据收益 | 封闭回归集 + 新场景集 + 现场对照 | 把测量基础设施算成模型进步 |

### 9.2 指标对照：每个数字回答什么、不回答什么

| 指标 | 回答什么 | 不回答什么 |
| --- | --- | --- |
| 成功率 | 在给定条件与口径下通过的比例 | 结果是否合格、是否需要人看护 |
| task success | 目标状态是否达成 | 质量、时限、损伤约束 |
| production pass | 在质量与时限约束下的合格交付 | 失败发生在哪一层 |
| 恢复率 | 偏差被发现并处置后回到有效状态的比例 | 恢复的代价与风险 |
| MTBI | 平均无干预自主时长 | 干预的风险分布与严重度 |
| 吞吐 / 质量 | 单位时间的合格产出 | 能力来自模型还是系统 |
| 安全事件 | 是否越过可部署边界 | 与成功率的可比性 |

这张表最实际的用法，是回答「为什么不能只报一个数」：每一行都有一个它明确不回答的问题，而那个问题恰好是另一行的定义域。

### 9.3 评测设计清单

| 检查项 | 要回答的问题 | 常见错误 |
| --- | --- | --- |
| 被测对象 | SUT 是模型、是「模型 + Prompt + 判分器」、是 Agent 系统，还是整机部署单元？ | 把系统指标当成模型能力，或反过来 |
| 评测单元 | 单元是任务实例、执行轨迹，还是一个班次的连续运行？样本之间是否独立？ | 用独立样本的统计方法处理相关轨迹与时间序列 |
| 协议冻结 | 任务卡、分组、判分与指标命名是否在首轮评测前冻结并版本化？ | 边跑边改口径，结果不可比 |
| 判分接口 | 判分能否复现？判分器自身是否被评测过？ | 判分逻辑混进被测侧，换模型即换口径 |
| 轨迹记录 | 是否记录中间决策、工具调用、超时、重试与错误码？ | 只存最终结果，事后无法归因 |
| 分层信号 | 各层是否有可观测判据？失败归属是否支持多标签？ | 归因靠印象，或强制单选把多因失败记成单因 |
| 成功口径 | task success 与 production pass 是否分开？成功是否按自主性分级？ | 把恢复成功与人工介入后完成混入同一分母 |
| 重规划质量 | 反馈是否真的改变了后续行为？ | 把重试成功一律记为「恢复能力」 |
| 分母与切片 | 稀有故障是否按运行小时 / 作业量？是否给出最差组？ | 只报绝对次数或总体平均，掩盖最差场景 |
| 安全 | 危险事件是否单列、是否具备一票否决？ | 把安全并入平均分，被一般失败稀释 |
| 版本对照 | 是否有封闭回归集、回归清单与回滚条件？ | 只报目标改善，不报遗忘与回归 |
| 结果报告 | 是否给出分布、波动范围、条件切片与不可比说明？ | 不同协议的数字并列比较 |
| 边界声明 | 是否区分「测量基础设施」与「能力提升」？ | 把评测服务写成训练成果 |

### 9.4 实施阶段与交付

分层不是并行铺开的清单，而是有先后的：口径没冻结，真机试验的返工成本最高。

| 阶段 | 具体交付 | 退出条件 |
| --- | --- | --- |
| 0 立项 | 目标场景、任务卡、质量标准、安全边界、基线版本与指标字典 | 业务方与评测方共同冻结口径 |
| 1 实验室 | 组件与开源 benchmark 报告；真机原子任务、泛化与恢复试验 | 关键任务达到预设门槛且无严重安全事件 |
| 2 连续运行 | 复合任务、工作流与多小时 shift 报告 | 干预需求和合格产出可接受 |
| 3 限域部署 | 站点分层仪表盘、故障闭环、版本对照 | 连续观察期稳定并满足客户验收 |
| 4 扩展 | 跨站点 / 跨机器人复制与持续改进报告 | 收益可复制，回归与安全门槛持续满足 |

最终评测包应包含：一页结论、任务与场景矩阵、全部分层结果、置信区间、失败案例及归因、风险与未覆盖范围、版本放行建议。**结论只给「在何种任务、环境、硬件和人工支持条件下可用」，不输出脱离边界的泛化总分。**

### 9.5 开放问题

- **归因的 ground truth 从哪来。** 目前分层归因依赖人工标注与工程直觉，缺少公开数据集。若有带层级标注的失败轨迹集，归因模型本身就可以被训练和评测。
- **环境非确定性下的可复现性。** 固定种子能带来可复现性，但也会让系统过拟合到特定扰动序列；真机评测则相反。如何在这两端之间取一个可比较的口径，尚无共识。
- **长程任务的统计功效。** 任务成功率低、单次运行成本高，意味着要区分两个系统往往需要很大的样本量。评测预算本身就是设计约束。
- **持续能力变化的评测。** 对 RoboCat、Voyager 这类会跨轮次积累能力的系统 [@19][@20]，以及 RISE、Q-Planning 这类把改进建立在世界模型或离线数据上的方法 [@21][@22]，单次成绩并不说明问题——需要在同一任务分布上重复测量「能力差」，而这类重复测量目前还缺少标准做法。
- **人工干预的分类学。** 「流程设计内的人工确认」与「能力不足导致的人工解救」需要分开统计，但两者在同一个看护指标下如何共存、如何跨场景可比，还没有通用做法。
- **质量分数的换算。** 连续质量分与硬性交付通过率之间缺少稳定映射；同一批结果按不同阈值切，会得到不同的「可交付」结论。
- **跨站点复制的适配成本。** 跨本体、跨标定的适配投入是复制部署难度的直接指标，但目前多以工时口径零散记录，缺少可比较的计量方式。

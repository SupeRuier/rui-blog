::: tldr
「统一多模态模型」这个说法里，最含糊的词是**统一**。它可以指统一任务、统一表示、统一时空尺度、统一训练阶段，或仅仅统一输出接口——这五层在架构上相互独立，而多数「统一」的争论其实源于双方在说不同的层。

本文的立场：

- **读到「统一模型」时，第一个问题是「统一的是哪一层」**。统一输出接口（都走一个解码器）和统一表示（理解与生成共用同一套视觉 token）是量级完全不同的声明。
- **数据与训练配比通常比单一结构选择更决定成败**。高质量图文对齐与 interleaved 数据不足时，把多任务混进一次训练未必收敛。
- **目标、方法、成果三者必须分开写**。本文只讨论目标与方法层面的架构问题——**没有完成全量训练，就不存在「成果」这一栏**。

本文不承担任何成果展示，也不以公开工作的成绩代替自己的工作。
:::

::: question
「统一」究竟统一任务、表示、时空尺度、训练阶段还是输出接口？不同架构路径之间有哪些冲突与验证要求？
:::

通用 VLM 更多处理「看见内容，输出语言」；统一多模态模型希望进一步处理图文交错输入、文本推理和图像／视频生成，让不同模态既能作为条件，也能成为输出。这里的「统一」不要求所有输入共用同一个编码器，而是要求清楚定义跨模态表示、共享主干、输出路径和训练目标。

## 「统一」统一的是什么：五个层次

把这个词拆开，它至少对应五层彼此独立的选择：

| 层次 | 统一的对象 | 主要冲突 |
| --- | --- | --- |
| **任务** | 理解与生成放进同一个模型 | 输出空间差异大，两类损失的权重难以平衡 |
| **表示** | 视觉用离散 token 还是连续特征 | 离散便于自回归与生成，连续更利于保留感知语义 |
| **时空尺度** | 图像、视频、长视频的时空结构 | 分辨率与帧率提升带来序列长度爆炸 |
| **训练阶段** | 先对齐再混合，还是从零联合训练 | 联合训练省掉阶段划分，但更容易能力互相牵制 |
| **输出接口** | 文本、视觉 token、动作 token 共用一个解码器还是各自头部 | 接口统一降低工程复杂度，但精度与延迟约束并不相同 |

这五层可以任意组合，所以「统一模型」通常只在其中一两层成立。**把统一接口说成统一表示、把统一表示说成统一训练，都是这个方向最常见的表述滑移。**

## 架构主线

一个简洁的抽象是：文本与视觉先经各自的 tokenizer / encoder 进入模型，组成带有模态边界和时序信息的序列；共享 Transformer 建模跨模态上下文；语言输出、视觉 token 解码或专门的生成头负责不同输出。视觉表示存在取舍：离散 visual tokens 方便把理解与生成放进自回归序列，连续视觉特征有利于保留感知语义；理解与生成对视觉细节的要求也不一样，因此可以共享主干但拆开编码／解码路径。[Emu3](https://arxiv.org/abs/2409.18869)[@1] 与 [Janus](https://arxiv.org/abs/2410.13848)[@2] 展示了两种可对照的设计，而不是唯一方案。

## 路径冲突：三组不能同时满足的取舍

架构选择之所以没有唯一答案，是因为下面三组取舍彼此对立：

1. **离散表示 vs 连续表示。** 离散 visual token 让理解与生成能共用一条自回归序列，工程上最简洁；连续视觉特征保留更细的感知信息，但生成侧需要一个额外的解码路径。[Emu3](https://arxiv.org/abs/2409.18869)[@1] 与 [Janus](https://arxiv.org/abs/2410.13848)[@2] 是这条轴上的两种可对照设计；生成侧还有连续流这一类选择[@5]。
2. **理解的语义需求 vs 生成的细节需求。** 理解需要抽象语义，生成需要像素级细节，两者对视觉编码器的要求方向相反。可行的折中是共享主干、拆开编码／解码路径。
3. **共享主干 vs 独立专家。** 共享带来参数效率与跨模态迁移，代价是能力相互牵制——改动一处会影响另一处，而这种牵制往往只在混合训练后才暴露。

第三组是实践中最难处理的。它意味着**混任务训练的失败常常不表现为不收敛，而表现为某一项能力悄悄退化**，因此必须逐能力设回退检查，而不是只看总 loss。

## 数据与训练，比单一结构更关键

训练样本需要覆盖纯文本、图文交错、视觉理解和视觉生成，并明确每种任务的输入、输出、模态边界、损失及采样比例。高质量的图文对齐与 interleaved 数据不足时，单纯把多种任务混进一次训练未必能够收敛，也可能让语言、感知或生成能力互相牵制。更稳妥的研究路线是依托已有 LLM / VLM 能力，先验证模态接入与单任务效果，再逐步混合任务、监测能力回退；数据版本、质量过滤、配比实验和误差切片应与结构选择一起设计。这一问题与[通用世界／具身理解 VLM 的训练、数据与评估](vlm-data-engineering.html)相连，但前者讨论理解／生成共用底座，后者讨论世界与具身理解能力的建设和验证。

## 能力边界与验证

评价不能只看图像生成质量，也要分别检查文本能力、视觉问答／grounding、图文交错理解、生成，以及跨模态多轮任务是否保持一致。机器人动作可以作为未来输出模态之一，但离散 Action Token 的序列预测与连续 Action Policy / 轨迹控制有不同的精度和延迟约束；把动作 token 拼进序列并不自动等于可部署的 VLA，也不意味着模型已经具备环境预测能力。动作侧的公开实现已经说明「把动作变成 token」在工程上可行[@3]，但**可行不等于统一**——动作输出的精度、延迟与安全约束仍与文本、图像输出不在同一个量级。理解侧则有能力、数据与训练三者对应的公开参照[@4]，可作为「统一前后是否真的都变好」的对照基线。这里暂不把 World Model、未来状态预测或视频生成机器人策略混作同一个架构目标。

## 目标、方法、成果：三者必须分离

这个方向最容易出问题的地方不是架构，而是表述。三件事必须分开写：

- **目标**：希望统一理解与生成。这可以是一句宏大的描述，因为它只是方向；
- **方法**：架构选择、数据配比、训练阶段设计、以及支撑这些选择的公开研究。它可以是推演，因为推演本身是有效的研究工作；
- **成果**：在哪些能力上、达到了什么**可复现**的水平，附对照与评测。

前两栏可以写得很大，第三栏必须能被复现。**缺了第三栏时，前两栏不应该以完成时态出现**——这是本文开头那条 note 存在的原因：它说明这是一个曾经设定、但尚未跑通完整训练与验证的方向。

后续可沿「表示接口 — 训练数据 — 验证指标」补充实验与公开系统对比；在没有完成训练前，保持目标、方法与成果三者分离。

::: my-take
判断一个「统一模型」的说法是否成立，我认为只需要问一句：**它统一的是哪一层？** 统一输出接口和统一表示是量级完全不同的声明——前者是工程便利，后者是架构主张。多数关于「统一」的争论，其实是双方在说不同的层，谁也没错。

而「目标、方法、成果」三者分开写，是这类方向最需要的自律。目标可以宏大，方法可以推演，但成果必须可复现；缺了第三栏的时候，前两栏就不该用完成时态。这既是对读者的诚实，也是对后续工作的保护——把方向说成成果，下一步就没有退路了。
:::

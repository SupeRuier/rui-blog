Robot Agent System 2：规划、执行与系统闭环

框架草稿：按能力、调度和系统边界整理 Embodied System 2；原 survey 的 init.md 待核对后补齐引用与具体系统实例。

System 2 不是一个更慢的动作模型，而是在长期任务中承担目标分解、状态理解和异常恢复的上层系统。System 1 的 Policy / Skill 处理高频执行，System 2 需要通过 Runtime 和环境持续闭环。

功能分类：上层到底做什么

  • Planner：把总体目标拆成子任务，选择下一阶段的 Skill / Policy、目标和执行条件。
  • Monitor / Critic：读取观测与执行反馈，识别环境变化、偏航、失败和需要重新规划的时刻。
  • Completion：判断子任务及总任务是否真正完成，而不只依赖动作步数或模型的自述。
  • Memory / Context：维护任务历史、已完成阶段、关键环境事实和恢复所需的状态。

运行分类：System 2 何时介入

比较系统时应区分一次性计划与闭环计划：按固定步数轮询、在子任务边界调用、由 Monitor 事件触发，或者在失败后重新规划。再比较输入是单帧、短期观测窗口还是带历史的上下文，输出是自然语言计划、结构化子任务还是可直接下发的 Skill 参数（参照层级调度研究[1]对比）。触发频率决定云端推理延迟、任务连续性和 System 1 是否必须等待。

系统分类：怎样和执行层接起来

Runtime 管理 Goal 状态、并发请求与超时，隔离云端 System 2 和端侧高频控制。Planner 输出经可校验的接口交给 Policy / Skill；执行反馈、失败原因和完成信号沿另一条链路回传。端侧负责安全、实时动作和必要的降级，云端更适合长时程推理与记忆；两者之间还需要定义抢占、重试和幂等边界。

评估轴

在相同任务和执行能力下记录成功率、子任务完成判定准确性、失败后的恢复率、Planner 调用次数与端云延迟，并保留 Trace / Replay。这样才能区分规划本身的收益、底层 Policy 的收益与调度策略的系统成本。可参照层级 VLA 调度研究与RoboOS 的公开设计对照这些轴[1][2]。
